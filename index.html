Claude Code cache, explained

and a practical guide to spending fewer tokens

Claude Code sends a lot of tokens on every turn. Your tools, your system prompt, your whole conversation history all get shipped to the model each time you press enter. If you paid full price for all of it on every request, the cost would be enormous. You do not, because of prompt caching. This article explains how that cache works, layer by layer, and then shows you where it quietly stops working and what you can do about it.

Everything here was measured on a real machine running Claude Code 2.1.226 talking directly to Anthropic. I captured live requests with a proxy and analyzed months of local usage logs. Where I cite a number, it comes from that data. Where I cite an issue, it is a link to a public report you can open and read. The links open the raw test results in a new tab so you can check the work yourself.

What prompt caching is

Prompt caching lets the model remember the beginning of your request so it does not have to reprocess it every time. When Claude Code sends a request, the server processes the tokens and can store the result. On the next request, if the start of the new request is identical to something already stored, the server skips the work and reuses the stored result. You pay a small fee to read from the cache instead of the full price to process the text again.

This matters because most of what you send does not change between turns. Your tool definitions are the same. Your system prompt is the same. The first twenty messages of your conversation are the same. Caching is what makes an ongoing session affordable: the stable front of the request is read from cache, and only the new tail is processed fresh.

What the pieces cost

To reason about caching you need the price of each operation. Everything is a multiplier on the base input price. Regular input is 1x. Reading from cache is 0.1x, a tenth of the price. Writing to the cache (storing something for later) costs more than plain input, because you are paying to process it and to store it. A write to the 5-minute cache is 1.25x. A write to the 1-hour cache is 2x. Output tokens, the model's actual reply, are about 5x.

Every token you send is billed at one of five rates. They are all multiples of the plain input price. Cache read is the cheapest thing on this chart, a rebuild at the 1h write rate is 20 times more.

Put those together and the shape of the problem appears. A cache read is 0.1x and a 1-hour cache write is 2x, so re-writing something you could have read costs twenty times as much. That 20x gap is the whole game. One avoided rebuild is worth twenty keep-warm reads of the same size. Hold that number; it is the reason the rest of this article matters.

In dollars, on Opus, per million tokens: input is $5, a cache read is $0.50, a 5-minute write is $6.25, a 1-hour write is $10, and output is $25. When I quote dollar figures later they are API-equivalent list prices, the value of the tokens, not a subscription bill.

What a request is made of

A single Claude Code request is assembled in a fixed order: tools first, then system, then messages. Each part has a very different size.

On a fresh main session where I typed only the word "hey," the request came to about 34,738 tokens. Tool definitions were about 16,295 of that. The system prompt was about 2,750. The messages were about 15,693, and inside the messages a single injected catalog block accounted for about 13,083 tokens on its own. The word I actually typed was about 1 token. Almost none of what you send is what you wrote.

One request is not your typed message. It is a stack: the tool catalog, the system prompt, then the messages. On a fresh main session that stack is about 34,738 tokens before you type a single word. The word you type is roughly one of them.

The messages layer is zoomed below. The catalog is the injected block that dominates it.

The order is correct and deliberate. Tools go first because they are the most stable and the most shared across every request. System comes next. Messages come last because they change most. Caching rewards exactly this: put the stable material at the front so it can be reused, and let the volatile material trail at the end where a rewrite is cheap.

Prefix caching and breakpoints

The cache does not store arbitrary pieces of your request. It stores prefixes. A prefix is the request from the very first token up to some marked point. Claude Code marks those points with a breakpoint, a small flag on a chunk of the request that says "this is a spot worth caching up to." A request can carry up to four breakpoints, and a prefix has to be at least about 1,024 tokens before it is eligible to cache at all.

When a new request arrives, the server compares it against what it has stored, starting from the first token. It reuses the stored prefix up to the deepest breakpoint whose fingerprint still matches, which is the last breakpoint before the first place the two requests differ. Everything before that point is read at 0.1x. Everything after it is processed fresh and, if it sits under a breakpoint, written back to the cache.

The consequence is strict: identical is not enough. The request has to be identical up to a breakpoint. If the first difference between this request and the last one is early, everything after that first difference gets rewritten, even parts that are byte-for-byte the same as before. The cache cannot skip ahead to a later matching island. It matches from the front, and it stops at the first change.

The fingerprint

The way the server tracks all this is worth understanding, because it explains why placement is everything. Each breakpoint carries a key that is a rolling hash of the entire token stream up to that point. Think of it like a git commit SHA: it summarizes the whole token stream up to that point, the chunk at the breakpoint and everything before it, cumulatively. The prefix at breakpoint four contains the prefix at breakpoint three, which contains the prefix at breakpoint two, and so on. They nest.

On a lookup, the server takes these fingerprints and finds the deepest one that still exists in the cache. It reuses everything up to that fingerprint, then recomputes and writes back everything after it. This is why a change early in the request is so expensive. It changes the fingerprint of every breakpoint downstream of it, because each of those fingerprints included the bytes you just changed. One early edit invalidates the whole chain below it.

How the cache stays warm, and when it expires

A cached prefix does not live forever. It has a time to live, a TTL, and the clock resets every time the prefix is read. As long as you keep using a session, each turn reads the warm prefix and pushes the expiry out again. The cache stays warm because you keep touching it.

There are two TTL settings. The default is 5 minutes. There is also a 1-hour option 9. A 5-minute prefix that goes untouched for six minutes is gone, and the next request rebuilds it from scratch at write price. A 1-hour prefix survives a coffee break and a meeting. The trade-off is the write price: a 1-hour write is 2x versus 1.25x for 5 minutes, so you pay more up front for the longer guarantee.

One avoided rebuild is worth 20 keep-warm pings on a 1 h cache, 12.5 on a 5 min cache. Same ratio at any prefix size.

This gives a rule of thumb for when keeping a cache warm is worth it. You must ping once per TTL to hold the prefix, and each ping costs 0.1x. Break-even, in idle hours, is roughly (write multiplier x TTL minutes) / 6: about 20 hours for the 1-hour cache, about 1 hour for the 5-minute cache. Past that idle threshold, let it die; below it, a cheap periodic read beats paying the rebuild.

Main sessions and subagents are built differently

Now the next layer, and it is a fact about how the two request paths are constructed rather than anything dramatic. When your main session sends a request, every breakpoint carries ttl=1h. When a subagent sends a request, the breakpoints carry ttl=5m(default). Claude Code omits the TTL field on subagent breakpoints, so they fall back to the API's 5-minute default. Your main session asks for the long cache; your subagents get the short one.

I confirmed this two independent ways, and it is worth keeping them separate because they prove different things. First, the wire itself: in the captured proxy log, all three subagent breakpoints show ttl=5m(default) while the main session shows ttl=1h 17. Second, the write volume at scale: a script over months of local usage logs shows main sessions wrote 1h=231,894,168 tokens (100% of main writes) and subagents wrote 5m=229,841,359 tokens (100% of subagent writes) 17. Across two machines the split held: main sessions 100% on 1-hour, subagents 100% on 5-minute.

One honest nuance. A subagent that spins up while riding an already-warm 1-hour prefix shared from its parent can write its small addition at the 1-hour tier. In one capture a subagent read 39,303 tokens and wrote only 25, and those 25 were written at 1h because they extended the parent's warm 1h prefix. That is a real edge case, not the rule. The single 1-hour subagent bucket in the aggregate (26,315 tokens) was a deliberate test run with the 1-hour flag forced on 17. The default subagent request is 5-minute, and nearly all subagent write volume is 5-minute.

Where it costs you

With the mechanics in hand, the problems are natural consequences, not surprises. Each one below is a symptom, a reason, and a citation you can open.

The final breakpoint sits behind the thing that changes. This is the root cause, and it is about placement, not content. In a captured subagent request, the layout ran in this order 18:

  1. tools (stable)
  2. system prompt, with breakpoints
  3. msg[0], the variable task prompt (about 1,250 tokens, ending in whatever word changed)
  4. msg[1], a stable block of about 9,500 tokens, the notice listing tools loaded on demand, with the final breakpoint at its very end

The problem is step 4 sitting behind step 3. There is no breakpoint between the variable task and the stable block behind it. So when one word in the task changes, the prefix invalidates from that word all the way to the end of msg[1], dragging the identical 9,500-token block into the rewrite along with it 7. The stable content is stranded behind the one thing that changes every spawn.

Subagents do not share a base with each other, so each spawn re-pays it. There is no cross-subagent prefix sharing. Every subagent writes its own base from cold. The base is the stable front of tools, system, and the notice block that has to be written from cold when nothing is cached 10. Across 40 real subagents, 25 of 40 started cold, the average base write was 34,051 tokens per spawn, and first turns ran 86% write to 14% read 23. Ten agents can turn into ten full base writes, which is the shape behind the "$400 for 10 agents" report 4.

A one-word difference rewrites about 14.6k tokens. Because the breakpoint is upstream of the task, two subagent prompts that differ by a single word do not share their tail. I sent two identical-except-one-word prompts (HEY vs HELLO): each wrote 14,623 and 14,624 tokens and read 11,602, for about 26,225 total each 7. Byte-identical prompts, by contrast, wrote 26,237 the first time and 0 the second time, reading the full 26,237 back. Identical costs nothing on the second spawn; one word costs you 14.6k.

Subagents on the 5-minute cache evaporate mid-fan-out. A fan-out where one agent takes six minutes leaves the others' prefixes expired before they are reused, forcing rebuilds a 1-hour TTL would have survived 38.

A dynamic line in a SessionStart hook poisons the cross-session catalog. This one has no issue filed against it directly, so I will be specific. If a SessionStart hook injects anything that changes between sessions (a UUID, a timestamp, a checkpoint path), it changes an early prefix, and the large stable catalog behind it can no longer be reused across sessions. In two main sessions where I typed only "hey," each read 21,478 tokens but each still wrote about 24,300, and the driver was a dynamic hook line, not the word I typed. This is the same class of problem as dynamic hook and injected content invalidating the prefix 1112.

The cch nonce is the thing people wrongly blame. The first system block carries a billing header with a cch=&lt;hash&gt; value that changes on every single request. It is tempting to blame it for cache misses. On native Anthropic it is a red herring. It has no cache_control, it sits above all the breakpoints, and main-session turns share huge growing prefixes with tiny writes even though cch changes every turn, which is impossible if it keyed the cache 17. It only hurts third-party routers that fold the header into their cache key, and the fix there is to set CLAUDE_CODE_ATTRIBUTION_HEADER=0 56. The real culprit is breakpoint placement, not the nonce.

Idle resumes, auto-compaction, and task nudges rewrite history. Coming back after the TTL expires rebuilds the base 13. Auto-compaction re-creates a stale large prefix 13. A task-reminder nudge injected into the history rewrites the cached conversation from the injection point down 14. Each of these is an early change with a long tail behind it.

Parallel tool calls and Agent Teams have their own rewrite modes. Parallel tool calls can collapse the cache read 16, and Agent Teams delivery has been reported as a full rewrite 15.

What to do about it

None of this requires patching Claude Code. Most of the recovery comes from a few habits and one or two settings.

Keep the main session warm instead of letting it die and rebuild. A periodic read (a cheap ping roughly every 50 minutes) holds the 1-hour prefix warm. Given the 20x rebuild-versus-read gap, this pays off up to about 16 hours of idle before the pings cost more than one rebuild. On the machine I measured, idle rebuilds were the single largest waste, and keeping warm recovers most of the roughly 13% of weekly quota that idle waste was costing.

Trim MCP servers you do not use. Tool definitions were about 16k tokens of base in every single session and every single subagent. That base is written cold on every cold start. Cutting unused MCP tools is the highest-leverage change because it shrinks a cost that is paid universally, on the main session and on every spawn.

Do not delegate trivial edits to a subagent. Every subagent spawn writes about a 34k base from cold. For a one-line edit you can do inline, that base is pure overhead. On the measured machine, a "delegate everything" habit ran 557 subagents and attributed roughly 1% of monthly quota, about $130 per month at API 5-minute rates, to spawn bases alone. That $130 is the delegate-rule attribution, not total spend.

When you do fan out subagents, make their prompts byte-identical inside the 5-minute window. Identical prompts write 0 on every spawn after the first; a one-word difference writes 14.6k each. Group subagents by type and hand them the same prompt. If the per-item detail has to vary, put it in a file the prompt points to (the prompt stays byte-identical while the file contents change), and the prefix stays fully cached.

Consider ENABLE_PROMPT_CACHING_1H=1, with a real caveat. This flips subagent writes to the 1-hour tier (measured: 1h=26,315, 5m=0 on the test run). It is a win only when you actually reuse the longer cache enough to cover the higher write price. A 1-hour write is 2x versus 1.25x for 5 minutes, so it pays off only when your rebuild-to-base ratio is above about 0.40. On one machine the ratio was 24.0M over 6.7M, or 0.28, a loss. On another it was 7.9M over 5.9M, or 0.74, a win. Measure before you flip it.

Stabilize your SessionStart hooks. Strip anything that changes per session (UUIDs, timestamps, checkpoint paths) out of what the hook injects early. On the measured setup this recovers up to about 24k tokens of cross-session write on every new session, because the large catalog behind the hook line becomes reusable again.
